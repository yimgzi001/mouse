# 性能检查记录（2026-11-17）

> 本文记录原生配置面板接入前的性能优化与当时采样。后续面板版本的短时采样见[面板验收记录](native-panel-validation-2026-11-17.md)；当前实现与待验收事项见[文档入口](README.md)。

结论：这台机器上当前链路已能接近摄像头的 30 FPS。主要开销是 ONNX 推理，不是手势映射。默认两线程可满足现有帧率；本轮降低了推理间隙的 CPU 空转，保留全部手势、灵敏度、分辨率和帧率。

## 环境与原版运行采样

- Windows，AMD Ryzen 7 5700U，8 核 / 16 逻辑处理器，ONNX Runtime 1.23.2，Go 1.27.2。
- 原版 `bin/mouse.exe -preview -verbose` 连续运行约 8 分 43 秒，退出汇总 15872 帧，处理 30.4 FPS，摄像头帧到输入处理结果平均 5.6ms。该均值包括大量没有执行推理的无人手帧，不能当作单手/双手模型耗时，也不包括传感器曝光、手势确认时间、预览绘制或目标应用响应。
- 在运行中的原版进程采样 30 秒，每 5 秒读取进程累计 CPU 时间、工作集、私有内存、线程和句柄。CPU 为整机归一化值：`100 × CPU秒增量 / 实际秒增量 / 16`。期间有单手活动，不能当成纯空闲基线。

| 秒 | 整机 CPU | 工作集 MB | 私有内存 MB | 句柄 | 线程 |
|---|---:|---:|---:|---:|---:|
| 5.1 | 4.40% | 100.0 | 92.8 | 601 | 23 |
| 10.2 | 5.08% | 100.0 | 92.8 | 601 | 23 |
| 15.2 | 8.41% | 102.6 | 94.1 | 624 | 23 |

这段短采样没有持续内存增长，不能代替长时间泄漏测试。原版日志最近 100 个采样/状态变化帧的耗时 p95 为 22.4ms，但采样偏向手势变化，不是全部摄像头帧的延迟分布。

## 可重复的模型链路对比

新增 `cmd/perfcheck`，只处理项目现有测试图片，不打开摄像头、不存摄像头画面、不发送桌面输入。模型加载、JPEG 解码和 20 帧预热不计入采样。每种场景实测 180 帧，按 30 FPS 节奏运行；整机 CPU 用该进程的 Windows `GetProcessTimes` 累计时间差计算，包含帧间等待，能反映空转成本。

- 无手：640×480 黑色 RGB 图；单手：`pointing_up.jpg`，358×376；双手：`right_hands.jpg`，720×382。所有对比在同一场景使用相同图片，不能把不同场景当作完全等尺寸输入。
- 测量范围：RGB 裁剪预处理、掌心检测、关键点推理和跟踪；不包含实际采集、手势/Windows 输入、预览绘制和调试日志。
- 以下是同一两线程配置的最终相邻两轮结果，采样时关闭了摄像头程序，避免同时运行干扰。测试图片在全部采样帧中分别稳定得到 0 / 1 / 2 只手。每个场景实际速率约 29.99 FPS，本组各 180 帧均无处理耗时超过 33.3ms 的样本。

| 场景 | 原默认 CPU | 新默认 CPU | 原平均 / p95 ms | 新平均 / p95 ms |
|---|---:|---:|---:|---:|
| 无手 | 2.31% | 1.35% | 3.32 / 15.43 | 3.68 / 16.22 |
| 单手 | 8.46% | 4.13% | 10.64 / 21.66 | 11.79 / 24.23 |
| 双手 | 9.41% | 6.51% | 16.42 / 21.11 | 19.86 / 22.33 |

双手平均多约 3.4ms，p95 多约 1.2ms，CPU 降约 31%；单手 CPU 降约 51%。这是资源与耗时的取舍，不宣称零延迟代价。单手还周期性检测第二只手，双手稳定跟踪时不再执行掌心检测，所以单手 p95 可能高于双手。

原始结果：`tmp/perf-spin-always-repeat.jsonl`、`tmp/perf-spin-run.jsonl`。之前还测试过完全关闭忙等（`off`）及四线程：完全关闭时双手平均约 20.3ms，出现 2/150 个超 33.3ms 样本；增加线程也提高 CPU，因此没有采用这两种配置作为默认。

## 修改内容及边界

- 模型默认使用 `session.force_spinning_stop=1`：一轮 `Run()` 结束后立即停止线程忙等，下一轮再恢复。该选项由当前 [ONNX Runtime 1.23.2 官方配置定义](https://github.com/microsoft/onnxruntime/blob/v1.23.2/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h)支持；[官方线程文档](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)说明了忙等对 CPU、功耗和响应的取舍。
- 只改变模型工作线程等待方式；没有降帧、降分辨率、更换/量化模型或修改手势识别阈值。
- `ModelOptions.WorkerSpinning` 提供 `run`（空值同默认）、`always`（旧行为）、`off`（完全禁用）供后续复测。正常用户界面不新增这些实现参数。
- 预览还会进行 RGB→BGRA 拷贝与 GDI 绘制，且绘制持有预览互斥锁；这是可继续测量的点，本轮没有单独量出它的成本，也没有据此改写绘图架构。
- 本次采样版本中，预览开启时 F8 暂停仍识别，关闭预览后暂停跳过推理。后续面板版本还会在存在启用的“手势暂停/恢复”绑定时保持观察，避免无法用手势恢复；摄像头仍保持打开。
- 当前采集只保留最新帧、复用缓冲；没有建立不断积压的帧队列。新优化没有改变这个设计。
- 不把 180 帧图片回放视作长时间真人双手验收，也不把帧处理耗时视作操作系统或用户感知延迟。

## 复测命令

在项目根目录运行，两次性能测试要先后执行，不要同时跑测试/构建或另一份摄像头程序：

```powershell
go run ./cmd/perfcheck -frames 180 -threads 2 -spin always
go run ./cmd/perfcheck -frames 180 -threads 2 -spin run
go run ./cmd/perfcheck -frames 180 -threads 2 -spin off
go run ./cmd/visioncheck -bench 80
```

`perfcheck` 输出 JSON Lines，含实际帧率、CPU、各分位耗时、超帧预算数、实际手数分布、检测次数及关键点推理次数。单独的 `visioncheck -bench` 是连续裸模型吞吐测试，不含预处理、跟踪及帧间等待，不能单凭它决定摄像头场景的线程数。
